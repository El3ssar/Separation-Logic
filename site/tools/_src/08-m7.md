@@ h3 [0]
The idea

@@ p [1]
Here is the design principle that separates separation logic from everything before it:

@@ quote [2]
A primitive specification mentions <b>only the cells the command touches</b>. Nothing else. Larger heaps are the frame rule’s problem, not the rule’s.

@@ p [3]
So the write rule owns exactly one cell, not “a heap containing that cell”:

@@ txt [4]
```
  { l ↦ old }        [l] := e        { l ↦ e }
  { l ↦ v }          x := [l]        { ⌜x = v⌝ ∗ l ↦ v }
  { l ↦ v }          free l          { emp }
```

@@ note [5]
kind: key
title: The one thing to remember
This is where the exactness of <code>↦</code> from M3 pays for itself. If <code>l ↦ v</code> merely meant <code>h l = some v</code>, the free rule would say “freeing one cell of any heap leaves the heap empty”, which is nonsense. Exact ownership makes the small rule <i>literally true</i>, and the frame rule then lifts it to arbitrary heaps without weakening anything.

@@ p [6]
Note also what the load rule does <i>not</i> do: it does not consume the cell. Reading is not destructive, so <code>l ↦ v</code> reappears in the postcondition, now next to a pure fact about the store. The pure fact is spatially empty — it owns nothing — which is exactly why <code>pure</code> rather than <code>fact</code> is the right choice on the left of that <code>∗</code>.

Exercises · the three primitive rules

@@ ex [8]
id: m7-1   name: hoare_load   hard: False
why: None
GOAL:
```
theorem hoare_load (x : Var) (l : Loc) (v : Val) :
    Hoare (l ↦ v) (.load x l)
      (pure (fun σ => σ x = v) ∗ (l ↦ v))
```
hint: The precondition <code>subst</code>s the heap to <code>Heap.singleton l v</code>; then <code>singleton_same</code> supplies the side condition of <code>Exec.load</code>. For the postcondition, split as <code>Heap.empty</code> ∗ <code>Heap.singleton l v</code>.
SOLUTION:
```
theorem hoare_load (x : Var) (l : Loc) (v : Val) :
    Hoare (l ↦ v) ((.load x l)) (pure (fun σ => σ x = v) ∗ (l ↦ v)) := by
  intro σ h hp
  subst hp
  refine ⟨⟨Store.set σ x v, Heap.singleton l v⟩, Exec.load (singleton_same l v), ?_⟩
  refine ⟨Heap.empty, Heap.singleton l v, disjoint_empty_left _, (union_empty_left _).symm, ⟨?_, rfl⟩, rfl⟩
  show Store.set σ x v x = v
  simp [Store.set]
```
expl: The whole proof is choosing the cut. The <code>pure</code> conjunct must own the empty heap, so the split is forced: <code>⟨Heap.empty, Heap.singleton l v, …⟩</code>. Then <code>disjoint_empty_left</code> and <code>(union_empty_left _).symm</code> discharge the two heap obligations, and <code>Store.set σ x v x = v</code> is one <code>simp</code>.

@@ ex [9]
id: m7-2   name: hoare_write   hard: False
why: The postcondition is written as an explicit lambda because it depends on the store: the value stored is <code>e</code> evaluated <i>in the final store</i>, which for a write is the same as the initial one.
GOAL:
```
theorem hoare_write (l : Loc) (e : Atom) (old : Val) :
    Hoare (l ↦ old) (.write l e)
      (fun σ h => (l ↦ (e.eval σ)) σ h)
```
hint: This is <code>write_singleton</code> from M1, wrapped in the triple.
SOLUTION:
```
theorem hoare_write (l : Loc) (e : Atom) (old : Val) :
    Hoare (l ↦ old) ((.write l e)) (fun σ h => (l ↦ (e.eval σ)) σ h) := by
  intro σ h hp
  subst hp
  exact ⟨⟨σ, Heap.write (Heap.singleton l old) l (e.eval σ)⟩,
         Exec.write (singleton_same l old),
         write_singleton l old (e.eval σ)⟩
```
expl: If you proved <code>write_singleton</code> in M1 as suggested, this is a single application. If you did not, you are now doing a <code>funext</code> plus case split inside a Hoare-triple proof, which is exactly the kind of layering violation the “separate heap algebra from program semantics” discipline is meant to prevent.

@@ ex [10]
id: m7-3   name: hoare_free   hard: False
why: None
GOAL:
```
theorem hoare_free (l : Loc) (v : Val) : Hoare (l ↦ v) (.free l) emp
```
hint: <code>erase_singleton</code>.
SOLUTION:
```
theorem hoare_free (l : Loc) (v : Val) : Hoare (l ↦ v) ((.free l)) (emp) := by
  intro σ h hp
  subst hp
  exact ⟨⟨σ, Heap.erase (Heap.singleton l v) l⟩,
         Exec.free (singleton_same l v),
         erase_singleton l v⟩
```
expl: Three lines, and the mathematical content is entirely in <code>erase_singleton : Heap.erase (Heap.singleton l v) l = Heap.empty</code>. This is the rule that would be unsound with an inexact <code>↦</code>; here it is trivial.

@@ ex [12]
id: m7-4   name: clearCell_spec   hard: False
why: None
GOAL:
```
def clearCell (l : Loc) : Cmd := .write l (.const 0)

theorem clearCell_spec (l : Loc) (old : Val) :
    Hoare (l ↦ old) (clearCell l) (l ↦ 0)
```
hint: It is literally <code>hoare_write</code> with <code>e := .const 0</code>.
SOLUTION:
```
def clearCell (l : Loc) : Cmd := .write l (.const 0)

theorem clearCell_spec (l : Loc) (old : Val) : Hoare (l ↦ old) ((clearCell l)) (l ↦ 0) :=
  hoare_write l (.const 0) old
```
expl: <code>(Atom.const 0).eval σ</code> reduces to <code>0</code> definitionally, so the specialised postcondition matches on the nose and no <code>hoare_consequence</code> is needed.

@@ ex [13]
id: m7-5   name: readAndFree_spec   hard: False
why: Read a cell, then give the memory back, keeping only the knowledge. The postcondition owns nothing — the value survives in a variable.
GOAL:
```
def readAndFree (x : Var) (l : Loc) : Cmd := .load x l ;; .free l

theorem readAndFree_spec (x : Var) (l : Loc) (v : Val) :
    Hoare (l ↦ v) (readAndFree x l) (pure (fun σ => σ x = v))
```
hint: You do not yet have the frame rule, so build the two-step <code>Exec</code> derivation directly with <code>Exec.seq</code> and prove the final heap is empty with <code>erase_singleton</code>.
SOLUTION:
```
def readAndFree (x : Var) (l : Loc) : Cmd := .load x l ;; .free l

theorem readAndFree_spec (x : Var) (l : Loc) (v : Val) :
    Hoare (l ↦ v) ((readAndFree x l)) (pure (fun σ => σ x = v)) := by
  intro σ h hp
  subst hp
  refine ⟨⟨Store.set σ x v, Heap.erase (Heap.singleton l v) l⟩, ?_, ?_, ?_⟩
  · exact Exec.seq (Exec.load (singleton_same l v)) (Exec.free (singleton_same l v))
  · show Store.set σ x v x = v
    simp [Store.set]
  · exact erase_singleton l v
```
expl: Do this once by hand, and notice the discomfort: to sequence the two rules you had to abandon them and go back to the operational semantics, because the load’s postcondition <code>pure … ∗ l ↦ v</code> does not literally match the free’s precondition <code>l ↦ v</code>. The missing tool is the frame rule, and M8 is precisely about earning it. When you come back in M9 you will redo this in two lines.
